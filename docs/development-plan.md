# CherryQuant 开发计划与应用节奏

## 1. 先做什么

不要从“完整量化平台”开始，也不要先做全功能画布。先完成一条从规则到解释再到版本比较的纵向切片：

`合成数据 → 规则确认 → 确定性运行 → DecisionTrace → 交易/无交易解释 → 复制修改 → 受控比较`

这条链跑通后，再决定哪些界面、数据源或更多条件值得投入。

## 2. 阶段与门槛

| 阶段 | 重点 | 进入下一阶段的门槛 |
| --- | --- | --- |
| M0 | 仓库、范围、契约、分支和测试策略 | 文档可定位；启动/测试方式明确；不声称已有产品 |
| M1 | 引擎、合成数据、黄金样本、异常路径 | 不依赖 UI 可重现完整实验；关键异常有测试 |
| M2 | 首条界面流程 | UC-01 至 UC-04 可跑通，图表与解释来自同一次运行 |
| M3 | 版本、比较、保存恢复、检验区间记录 | UC-05 至 UC-07 可跑通，旧运行不被覆盖 |
| M4 | 小范围受控试用 | 目标用户能完成任务；真实数据、权限和限制说清楚 |
| M5 | 反馈驱动扩展 | 每次增加能力都对应明确的用户阻塞和可检查改善 |

## 3. 单人项目的周期管理

采用短周期而不是大而全的里程碑。每个周期只承诺一个可演示结果：

1. 周期开始：写清一个用户问题、一个可验证假设、一个不做清单。
2. 周期中段：先写契约和测试样例，再写实现；尽早用小数据跑通。
3. 周期结束：演示完整路径，记录已完成/已测试/未完成/已知限制，合并一个小 PR。
4. 周期复盘：把问题分成软件理解、数据质量、策略语义和工程可靠性四类，只处理最高频阻塞。

建议同时只维护 1 个主开发目标和最多 2 个支撑任务，避免 UI、数据、引擎和商业化同时开工。

## 4. 如何平衡开发与应用

在 M1-M3 期间，应用不是“等产品做完再做”，而是用受控任务验证可理解性：

- M1：自己用人工可核对的合成样本验证计算和解释。
- M2：请 1-2 位熟悉 K 线但不会编程的人完成搭规则、解释交易/无交易的任务。
- M3：让其修改一个条件、比较两版并恢复实验，观察是否能说清改动影响。
- M4：只开放支持范围内的受控数据和账户，不把开发服务器直接暴露到公网。

每次试用只问“用户在哪一步卡住、误解了什么、是否能自行继续”，不要用一次收益曲线好坏替代产品验证。

## 5. 资源分配建议

在没有用户阻塞证据前，优先级大致为：

1. 计算正确性与可追溯记录；
2. 规则确认和解释体验；
3. 版本与比较；
4. 数据授权、隔离和资源限制；
5. 新条件、股票池、自然语言辅助等扩展。

开发和应用的平衡点不是平均分配时间，而是每个技术增量都尽快转成一个可观察的用户任务；若一个功能无法改善任务完成或理解，就延后。

## 6. 完成定义

一个任务只有同时满足以下条件才算完成：

- 有契约或决策记录；
- 有自动测试或可复核样例；
- 有明确的失败/限制展示；
- 不覆盖旧版本或旧实验；
- README 或阶段文档能说明如何运行；
- 能用一句话说明对用户任务的改善。
