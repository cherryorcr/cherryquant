## 1. 用户已确认的方向与尚未确认的建议

### 1.1 已确认

- 希望由一个人开发，面向个人用户，先做 MVP，再让人使用并迭代。
- 目标用户不是 AI 重度用户或程序员，而是有自己交易经验、希望把经验规则化的 A 股投资者。
- 用户自己制定交易规则；产品负责帮助表达、检验、理解和迭代这些规则。
- 可视化不只用于看结果，还要帮助定位问题、修改策略、检查修改的影响。
- 可信度重要：需要知道规则怎样运行、为何触发、数据依据是什么。
- 后续统一在 `cherryorcr/cherryquant` 开发。

### 1.2 本文建议的默认值，并非用户逐项拍板

- 首版采用单标的、日线、只做多、不加杠杆的历史规则实验。
- 首批模块只覆盖有限价量条件、入场、退出与仓位；暂不开放任意代码或自由连接所有模块。
- 首版不依赖大模型，不接实盘；自然语言辅助、舆情、股票池与组合能力后续逐步加入。
- 技术栈建议 React/TypeScript/Vite + Python/FastAPI/Pydantic + SQLite。
- 首次体验以本地或受控环境为主；公开部署另设安全、数据授权与合规检查。

这些默认值是为了尽快跑通流程。接手者可以根据实际仓库、用户补充和实现验证调整，但应记录原因，不要默默把它们说成既有决定。

### 1.3 仍然未知

商业数据授权及报价、具体产品的监管边界、用户真实付费意愿、可承受的投入与工期、最终 UI 形态、正式技术选型。

## 2. 产品核心与 MVP 成功标准

### 核心任务

“我有一套买卖方法，但不会写公式。我想把它搭出来，检查它在历史上到底怎样运行；发现问题后修改，再比较改动有没有产生预期影响。”

### 核心闭环

选择数据 → 搭建并确认规则 → 运行历史实验 → 在 K 线上查原因 → 创建修改版本 → 在相同条件下比较 → 保存并继续研究。

“优化策略”在本产品中指有依据地提出修改并验证影响，不等于自动搜索出最高历史收益，也不承诺修改后盈利。

### 两种不同的成功

- 工程成功：计算、交易假设和解释记录一致，可复现、可测试。
- 用户成功：不用编程即可发现一个具体问题，修改规则，并解释两版结果为何不同。

收益上升不是 MVP 验收条件。结果变差、没有交易或发现经验不可靠，也可以是有价值的实验结果。

## 3. 范围边界

### 3.1 v0.1 必须有

- 选择一份固定数据与一个标的，查看来源、覆盖范围和价格口径。
- 使用少量条件卡片配置规则，并生成可读确认单。
- 运行确定性的历史实验，区分失败、无交易和正常亏损。
- K 线、交易标记、逐日条件判断联动。
- 解释“为何买卖”“为何没触发”“为何触发但未成交”。
- 修改生成新版本，保留旧规则、旧运行和修改理由。
- 在相同实验条件下比较两版规则、交易变化和结果。
- 保存并恢复实验；导出规则和摘要，不默认导出无再分发权的数据。
- 明示研究区间与保留检验区间，记录检验区间是否已查看。

### 3.2 首版暂不做

全市场动态选股、多标的资金分配、任意自然语言生成可执行代码、自由 DAG、机器学习预测、实时舆情、盘中止盈止损、多券商接入、自动下单、自动调参、策略商城、收益分成、完整支付体系。

单标的实验不等于全市场选股，也不能证明策略具有跨股票、跨行情的普遍有效性。若首批用户最主要的需求就是选股，应据试用结果调整下一阶段，而不是把单标的演示宣传成已经解决。

### 3.3 推荐的交互起点

默认使用“入场条件—退出条件—仓位—运行假设”的卡片，而不是要求普通用户理解复杂连线图。结果区以 K 线和解释面板为主，版本比较为独立视图或展开区。

首轮模块可从收盘价与均线关系、均线交叉、成交量相对均量、固定仓位上限等少量已测试条件开始。它们只是技术演示部件，不是推荐投资方法；具体模块与参数应在契约阶段确定。

## 4. 端到端用例与验收

### UC-01 选择实验数据

- 前提：进入示例项目或已授权的数据项目。
- 操作：选择标的、研究日期范围与保留检验范围。
- 结果：展示来源、数据版本、频率、复权/价格口径、覆盖范围和已知限制。
- 异常：超范围不能静默补齐；保留检验区间必须晚于研究区间且互不重叠；指标预热不足显示“数据不足”；合成数据醒目标为演示，不展示为真实市场表现。
- 验收：数据来源、版本及实际使用范围写入实验记录。

### UC-02 搭建并确认规则

- 前提：使用平台已支持的条件卡片。
- 操作：设置入场、退出、条件组合、仓位与实验参数。
- 结果：得到可读的规则确认单，说明何时观察条件、何时尝试成交。
- 异常：缺少必要字段、非法参数、已知冲突或不支持的组合不能直接运行；提示具体原因。
- 验收：所有默认值可见；草稿与已确认版本区分；系统不擅自补充投资逻辑。不承诺识别所有可能的逻辑矛盾。

### UC-03 运行历史实验

- 前提：用户确认了规则、数据与运行假设。
- 操作：点击运行。
- 结果：创建新运行，固定规则、数据、引擎、费用与成交假设快照，生成结果及判断记录；状态通过事件演进，输入快照与完成结果不被覆盖。
- 异常：运行失败、数据不受支持、无交易、策略亏损必须分别呈现；不得将错误显示为零收益。
- 验收：相同内容快照与配置产生相同的确定性结果；运行 ID 和时间戳可以不同。

### UC-04 在 K 线上检查任意一天

- 前提：实验正常完成。
- 操作：点击研究区间或已解锁检验区间的日期、买卖标记或交易记录；未解锁区间不能通过图表、比较或导出提前查看。
- 结果：显示条件输入值、阈值、通过/未通过/无法判断、最终信号及模拟订单状态。
- 异常：停牌、价格限制、现金不足等造成未成交时，显示原因；无信号日期同样可检查。
- 验收：信号时间与模拟成交时间分别显示；图表和解释读取实际运行记录，不独立重算，更不能事后由 AI 编造理由。

### UC-05 定位问题并创建新版本

- 前提：用户发现规则与预期不符，或提出新的投资假设。
- 操作：复制旧规则，修改一个或少量条件，记录修改原因和预期影响。
- 结果：生成带父版本的新版本，显示改了什么，旧规则与旧结果保留。
- 异常：区分“改变策略”与“修复软件计算错误”。修复引擎错误应升级引擎版本，并标记受影响旧运行，不能偷偷覆盖。
- 验收：修改界面、重新运行或保存均不改变既有实验。

### UC-06 同条件比较两版策略

- 前提：选择两个运行结果。
- 操作：比较规则差异、交易增减、决策日期变化与风险收益结果。
- 结果：用户能解释哪条改动改变了哪些交易，而不只看到两条收益曲线。
- 异常：数据、范围、初始资金、费用、成交假设或引擎版本不同，明确标为非受控比较，提供在共同条件下重跑的选择，不能静默混比。
- 验收：失败/无交易版本仍能正确展示；不自动将历史收益更高的一版标为“更优策略”。

### UC-07 保存、恢复和复查

- 前提：实验已保存。
- 操作：关闭后重新打开，查看规则、结果及解释。
- 结果：恢复原实验快照；数据后来更新不改写旧结果。
- 异常：快照不可用或指纹不符时，不冒充原实验重跑成功。
- 验收：可以导出规则、运行摘要和已知限制；原始数据导出遵循授权。

## 5. 首版必须写清的计算与交易语义

这些是引擎开发前的契约，不应由 UI 或模型临时决定。

- 仅在日线收盘数据完整后观察条件，最早于下一交易日开盘尝试模拟成交；不能默认按生成信号时的同一收盘价成交。
- 明确订单有效期：建议首版只尝试下一交易日，无法成交则记录原因并取消，后续由新的日终判断决定；如改为顺延，应另写可测试规则。
- 单标的、只做多、不加杠杆；仓位、手数、现金和费用必须纳入计算。
- 按所支持普通 A 股范围执行 T+1；不把其他品种的当日回转规则套用进来。
- 对停牌、价格限制和可成交性采用明确、保守的日线模拟假设，不声称复现真实排队成交。
- 交易限制、费用和价格口径具有版本或适用范围；不能把统一涨跌幅比例和当前费率无条件用于所有历史股票。
- 首版不推断同一天内止盈与止损的先后；不支持的盘中路径明确拒绝，而非取对收益更有利的顺序。
- 指标计算价格与模拟成交价格的口径必须分清；公司行为、分红复权不可静默忽略。合成测试可先不含公司行为；真实数据若跨越尚未支持的事件，应阻止相应研究并说明限制。
- 缺数据、指标预热不足、条件不成立是不同状态，不能全部变成 false 或零。
- 对应现有持仓时先处理退出，不在同一撮合时点又退出又重新入场；更复杂模式后置。
- 如末日仍持仓，区分浮盈估值与已实现收益，不制造不存在的平仓成交。

## 6. 数据契约与可信架构

| 对象 | 必要内容 |
| --- | --- |
| `StrategySpec` | 版本 ID、父版本、标的、条件与参数、组合方式、进出场、仓位、观察/执行时点、用户确认状态 |
| `DataSnapshot` | 来源与使用权限说明、标的/区间、内容指纹、字段定义、交易日历、价格口径、交易限制字段、缺失和已知限制 |
| `ExperimentConfig` | 初始资金、费用和成交模型、引擎版本、固定的研究区间与保留检验区间定义 |
| `Run` | 固定引用上述对象；状态事件、结果、失败原因和警告；输入快照与完成结果不可原地覆盖 |
| `ExposureLog` | 按项目、标的和时间区间追加查看/解锁事件，记录所见数据版本；跨实验保留，不通过复制策略或更换快照自动清除 |
| `DecisionTrace` | 观察时点、条件输入/阈值/状态、信号、模拟订单、成交/未成交及原因、相关价格与费用 |
| `Comparison` | 两个运行引用、规则差异、可比性检查、交易差异和结果变化 |

架构原则：

- 同一份规则定义驱动计算、可读说明和后续模拟；不是每个模块各自解释一遍。
- 引擎独立于 API、图表和大模型，能用小数据直接测试。
- 解释来自 `DecisionTrace`。条件成立、信号产生、订单创建和订单成交是不同事件。
- 运行输入和结果保留版本与内容指纹；数据升级、规则修改或模型变更生成新运行。
- 若以后加入 AI，只允许其辅助提出结构化草稿、解释已记录事实；用户确认后，确定性引擎负责执行。

## 7. 防止“可视化优化”变成过拟合工具

首版不做自动调参，但必须保留最基本的实验纪律：

1. 运行前记录研究区间与保留检验区间；保留区间在时间上更晚且互不重叠，不强行规定一个适合所有策略的时间比例。指标预热只使用当时之前可获得的数据，不能用完整历史数据预先拟合参数或标准化。
2. 修改策略时保留版本、修改理由和实验历史，不只保存表现最好的一版。
3. 反复修改、比较主要发生在研究区间。
4. 候选规则确认后才解锁保留检验区间，将查看事件追加到独立的 `ExposureLog`，不修改实验输入快照。解锁前，接口、K 线、交易、解释、比较、导出及收益展示均不能泄露该段实验数据或结果。
5. 查看后再据此改规则，该段数据不能继续被称为未见数据；新建名称或复制实验不能清除这段使用记录。
6. 平台只能记录平台内的查看情况，不能保证用户在外部从未见过数据。
7. 后续前向模拟使用冻结版本；改规则开始新的版本和跟踪段，不重写旧成绩。

这套机制不保证避免所有过拟合，也不证明未来盈利。首版可以只提供研究/保留两种区间，独立验证区间和更复杂研究工具后置。

## 8. 建议工程起点

这是待实现时确认的建议，不是已存在的技术栈。

- 前端：React + TypeScript + Vite，条件卡片、K 线、逐笔解释、版本比较。
- 后端：Python + FastAPI + Pydantic，统一校验契约并调用引擎。
- 存储：SQLite 存策略、实验与索引；文件保存固定数据快照和较大运行结果。
- 图表：选择允许目标用途的 K 线组件并遵守署名；上线前核实具体版本许可。
- 执行：限制单次数据规模和并发；先用简单受控执行器，不先引入分布式任务系统。
- 测试：引擎单元/黄金样本测试、API 契约测试、前端关键交互测试与完整流程测试。

建议目录：

```text
apps/web/             前端
apps/api/             HTTP 层与任务入口
packages/engine/      规则、计算、成交模拟与追溯
contracts/            共享契约与示例
fixtures/             自编合成数据、人工可核对结果
tests/                跨层与端到端测试
docs/                 产品范围、用例、技术决策、数据与交易假设
```

不为演示预先建设登录支付、策略市场或微服务。若对外提供托管试用，访问控制、用户隔离、资源限制和私密策略保护必须在开放前补齐，不能把无鉴权开发服务器直接暴露到公网。

## 9. 开发阶段与完成门槛

| 阶段 | 工作 | 完成门槛 |
| --- | --- | --- |
| M0 仓库与契约 | 在目标仓库建立工作区；检查指令与状态；保存本交接和范围/交易语义决策；确定依赖与许可 | 文档可定位，建议与确认事项区分，启动/测试方式明确；尚不声称已有产品 |
| M1 可核验引擎 | 合成数据、规则校验、单标的事件流程、费用与现金、逐日记录 | 人工可核对样本和关键异常测试通过；无 UI 也能重现一次完整实验 |
| M2 首条界面流程 | 数据选择、条件卡片、确认、运行、K 线与解释联动 | UC-01 至 UC-04 跑通，包括无交易、失败、无法判断和未成交路径 |
| M3 迭代闭环 | 新版本、修改理由、受控比较、保存恢复、区间查看记录 | UC-05 至 UC-07 跑通；能解释改动造成的交易变化，旧实验不被覆盖 |
| M4 受控用户试用 | 核实真实数据权利和质量；完善支持范围；必要的访问与资源限制；操作指引 | 目标用户能完成真实任务；演示与真实研究明确区分；阻断尚未支持的场景 |
| M5 反馈驱动扩展 | 根据阻塞决定增加条件、股票池/组合或自然语言辅助 | 每次迭代有具体用户问题及可检查的改善；不以功能数量作为进展 |

M1 至 M3 构成首个技术闭环；合成数据只证明流程和计算实现，不证明真实策略价值。M4 需要允许该测试用途的真实数据，不能用漂亮的合成收益替代。

本轮没有为任何阶段承诺日历工期；拿到真实实现和数据约束后再估算。

## 10. 自动化验收清单

## 11. 第一轮试用怎样收集反馈

寻找懂基本 K 线、有一条相对固定规则、不会编程的少量测试者。不以样本人数达到某个门槛就宣称市场成立。

请其完成一个任务，而不是先填写泛问卷：

1. 用自己的话说明规则；搭完后复述系统实际会怎么做。
2. 解释一次交易和一次没有交易。
3. 找出一个与原本预期不同的行为。
4. 提出一条修改理由，生成新版本。
5. 对比两版，说明预期影响是否发生。
6. 稍后自行恢复实验，决定下一步要检验什么。

记录其卡在哪里、需要几次帮助、误解了什么、能否自行修改、是否愿意再次使用。策略好坏、软件理解错误、数据问题和界面问题要分开归类。

未经同意不要收集真实持仓或公开其策略；不把用户策略默认用于跨用户学习。试用后按反复出现的阻塞排序，而不是立刻响应每一个长尾功能请求。
